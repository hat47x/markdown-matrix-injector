# ExcelとMarkdownを併用する執筆作業からの要件見直し

Status: Active / 2026-10-08

既存のExcel設計書を踏襲してMarkdown文書と共存させる仕事を第一に、新しい表をExcelで作る仕事も支える。文化的体系から得た案も、VS Codeで資料や本文を書く際に何が助かるかで選び直す。判断の正本は[製品要求](../00_Prompt/requirements.md)と[ADR-0019](adr/ADR-0019-ai-era-sier-document-value-and-policy.md)、作業は[issue-0211](https://github.com/hat47x/markdown-matrix-injector/issues/514)で追う。

## 1. 選び直した理由

前の計画では、条件付き比較の入出力を定義できたことを、実装を先行させる根拠にしていた。しかし、引用の選択、意味対応、条件集合、用途、理由を別の作業票へ入力する準備が、普段の執筆を助けるかは確認していない。処理を定義できることと、利用者の仕事に採用すべきことを分ける。

条件付き比較のissue-0209はDraftへ戻す。条件節を添えるissue-0210もDraftとし、まず通常のMarkdown追記で十分かを調べる。最初に進めるのは、実装済みの参照作成・補完・表の目録を使い、既存設計書と新規表の双方で執筆を続けられるかを確かめ、不足を直すことである。Linkedでの継続利用は、それ自体が成立する使い方である。

## 3. 同じ作業で確かめる六つの場面

以下はこれから使う受入用の作例であり、実務観測の結果ではない。既存設計書の試用には、利用許可のある資料またはその構造を再現した材料を使い、新規表だけで代用しない。

| 場面 | 書き手がすること | 合格を判断する成果物・操作 |
| --- | --- | --- |
| A 既存設計書を踏襲 | 原本の書式を変えず、必要な画面項目表を選び、Markdownへ説明を加える | 原本と選択範囲が一致する参照と本文が残る。全ブック変換を要求しない |
| B 新しいExcel表 | 既存ブックに表・シートを追加する場合と、新規ブックを保存する場合を試す | 目録または案内付き作成から参照できる。推定候補が不適切なら範囲を明示できる |
| C 保存後の値変更 | Excelで値を直して保存し、VS Codeへ戻る | 現在の保存内容をプレビューで確認できる。手動再描画が必要なら分かる手順がある |
| D 行列・構造の変更 | 固定範囲外への行追加、範囲内への挿入、見出し変更、シート名変更を別々に試す | 追加行が含まれるかを確認し、人が範囲・条件を直せる。A1範囲が解決しただけで意味の追従を成功としない |
| E 修正・取消・再開 | 参照元を確認し、一部の指定だけ直す。途中取消と確定後のUndoも行う | 周囲の本文・未変更の指定を保ち、元の執筆位置へ戻れる |
| F 不在・取得不能・曖昧 | ブック移動・削除、一時的な読込み失敗、似た表が二つある状態を試す | 原因と次の操作が分かる。古い表示や似た表へ自動で置き換えて成功としない |

値の更新と構造の更新は別に扱う。`A1:D8`の9行目に足した行は範囲外であり、自動拡張を約束しない。また、範囲内へ行を挿すと、参照は解決していても末尾が外れる場合がある。まず書き手が対象を確認・修正できる経路を成立させ、構造差分の自動警告は、検出根拠と誤警告の負担を確かめてから追加する。

## 4. 体系に基づく深掘りを執筆へ戻す

以下は[発想地図](cognitive-cultural-opportunity-map.md)と[境界の分析](cognitive-cultural-boundary-analysis.md)で扱った操作を使う設計上の類推である。文化体系について新しい史的主張を加えたり、MMIでの効果を実証したりしたものではない。

### 4.1 パターン・ランゲージと華厳から、反復する仕事と文脈を分ける

「本文を書く→表を選ぶ→確認する→説明を続ける」を、既存表と新規表に共通する仕事として取り出す。同じ表でも、画面仕様の章では入力項目、移行計画の章では対象データの説明になる。参照を共有しながら、用途ごとの説明はMarkdown本文に残す。

ここから必要なのは、参照の再利用と直しやすさである。用途を分類する大きなフォームを先に作ることではない。通常の一段落で説明できるならそれを使い、同じ条件節を何度も選び直す実際の負担が見つかった場合だけissue-0210を再検討する。

### 4.2 波航海術の手掛かりとニヤーヤの適用点検から、選択の根拠を残す

表題、シート名、見出し、原本座標は、目的の表へ辿る手掛かりになる。手掛かりが似ていることと、今回の用途に正しい表であることは同じではない。目録の候補から実描画を見て確定する既存経路を優先し、似た表の自動確定を避ける。

反例は、同じ「画面項目」見出しを持つ旧版と新版である。候補件数を減らすだけでは誤選択を減らしたことにならない。受入時には書き手がファイル・シート・範囲を説明できるかを確かめる。候補がない場合も、ブック未保存、未取得、検出不能、範囲内に表がない状態を一括して「表なし」としない。

### 4.3 ジャイナの条件付き叙述から、表示の成立条件を絞る

本文の意味条件を専用作業票へ入力させる前に、「どの保存済みファイルの、どの範囲を、どの変換条件で見ているか」を確認対象にする。これならEW03〜EW05の具体的な操作へ戻せる。

Excel上の未保存値、保存済みの数式キャッシュ、画面上のフィルター、MMIの行絞込みは同じ根拠ではない。例えば、Excelで行を非表示にしたからMMIでも除外されたはずだと判断せず、記法と描画で対象を確認する。実際に表示する条件と制約を案内し、毎回すべての業務条件を入力させない。

### 4.4 Bauhausと易の構成変更から、修正箇所を一つずつ確かめる

表現を操作して確かめる考え方を使い、値だけの変更、行追加、列追加、見出し変更、シート名変更を別々の材料にする。複数変更をまとめて「更新できた」とすると、値追従の成功で範囲の欠落を見落とす。

既存の参照編集では、直す指定だけを変え、実描画で確認して一回の編集として確定する。参照の自動再束縛や範囲の自動拡張を追加する前に、この小さな修正が執筆を妨げず行えるかを確かめる。

### 4.5 ラサから、受け手が読み取ったことへ評価を戻す

支援案の評価を、注記の数や生成した問いの数で終えない。書き手が「どの表を参照しているか」「何を保存すれば反映するか」「行を追加したら何を直すか」を説明し、実際に修正できるかを見る。読み手には、表と本文から適用条件や次の操作を説明してもらう。

これは本計画の評価方法への類推であり、感情や文化的効果を機械的に採点する案ではない。準備や確認が増えて普段の作業が遅くなるなら、専用支援を採用しない判断も記録する。

## 5. 今回の要件と探索の境界

要件へ取り込むのはEW01〜EW07であり、まずissue-0211で既存機能をつないで確認する。追加の意味比較、文脈の自動推薦、判断継承の専用画面は採用を保留する。読解経路N01は「書き手が実際の原本へ辿れるか」、継承N02は「再開時に何の表を何のために選んだか分かるか」へ戻して分析を続ける。通常の参照とMarkdownで足りない具体例が得られた要素から次の計画へ移す。
