## 1. 開発形態の方針

**MMIという呼称は現在のVS Code拡張の名称として残す。** 補助CLI、MMI Notation、公開契約などの既存識別子を維持し、実験的アプリケーションとして開発と実利用を続ける。MMIに本流の独立Desktop製品を前倒しで実装することを目的としない。

**将来の本流製品は別途開発する。** TEIの必要なDesktop／Plugin／Host機構が成熟した後、Wailsを用いる独立したDesktopアプリケーションを開発する方針とする。名称、具体的な実装構成、MMIコードからの継承範囲、提供時期はここでは定めない。

両者の関係は、単なる旧版／新版ではない。MMIはSIer文書ドメインの要求・失敗例・有効な操作・検査基準を見いだす**継続的PoC**であり、将来製品はその知見を踏まえて再設計する。MMI側の改善は継続し、実際に使えることを実験の前提とする。

### 既存の提案・判断との関係

- ADR-0019の「書き手を止めない」「原本を非改変」「Linked / Extracted / Detachedを情報単位で選ぶ」「生成AIへ安全な事実と候補を渡す」を維持する。
- ADR-0024は**Proposed**であり、上位製品名を新設して既存製品の総称を変える旧案を含む。今回の「MMIをVS Code拡張の呼称として残し、将来の独立製品は別途開発」という方向を反映し、#504で範囲と前提を再整理する。ADR-0024を採択済み、候補名を決定済み、既存実装の改名が必要とみなさない。
- VS Code拡張、CLI、Notationの実際の互換性と実装位置は現行コード・記法仕様を正本として確認する。本書の構想によって実装状態を更新したことにはならない。

## 2. MMIで試す最小のドメインシナリオ

出発点は、**納品対象の既存Excelファイルを一つずつ参照するMMI記法を列挙したMarkdown一枚**でよい。原本Excelの書式や運用は変更しない。

```markdown
# 基本設計 納品構成
## 設計資料
![[./excel/screen-design.xlsx]]
![[./excel/data-design.xlsx]]
## 試験資料
![[./excel/integration-test.xlsx]]
```

シートを指定しないMMI参照は現行実装では別紙カードになる。既存 `mmi manifest` は**カード扱いとなる参照の一覧**を生成するが、ファイルの実在確認、参照元文書を含む全依存の閉包、契約で求められる納品物の網羅性を保証しない。この区別を保ちながら #658 で実用性を検証する。

実験の順序は、(a)文書体系全体をまず捕捉、(b)ファイル・シート・表・図・見出し等の構造を必要に応じて観測、(c)人と生成AIがMarkdownへ取り込む本文や表を選択、(d)Excel側を必要に応じて細分化／図表別紙化、(e)出典と検査結果を保って再構成する、というもの。**全ExcelをMarkdownへ置換することも、全情報を初期時点で意味解析することも必要条件ではない。**

## 3. 文書体系と納品品質の検証候補

| 論点 | 確認したいこと | 注意する境界 |
| --- | --- | --- |
| 文書集合 | Markdown＋MMI記法から納品対象のファイル・見出し位置・参照関係を導出する | 手入力した第二の納品台帳を正本にしない。通常の参考リンクは納品指示と同じとは限らない |
| 形式 | 原本の実形式と、Markdown/PDF/DOCX等の納品形式を区別する | 拡張子の推定だけで対応済みにしない |
| 納品の網羅性 | 要求成果物（外部要求）、宣言された成果物、実際の配置・生成物を照合する | 参照先が全て存在しても、契約上の必須文書の存在は保証できない |
| 納品の完結性 | 欠落・重複・古い版・境界外参照・未収録依存資産を検出する | 解析できない範囲をPASSにしない |
| 見出し・目次 | 文書内外の章節、図表、相互参照を追跡し構成変更へ利用する | 明示構造と推定構造を区別する |
| 文書関係 | Document／Section／Table／Figure／Source／Artifactの関係を導出する | 「Document Graph」は論理候補。独立DBや新しい正本を先に設けない |
| リファクタリング | Linked／Extracted／Detachedの混在を保ち、移動先・出典・情報の欠落候補を追跡する | 同じ内容・同じ原本位置・同じ意味を混同しない |
| AI検査 | AIへ文書全体像、関連箇所、原本座標、鮮度・未解析範囲を渡し横断検査を助ける | AIの推定や指摘は権威・人の採否・形式検査合格の代替にしない |
| 最終出力 | 顧客様式、本文、図表、別紙、納品一式を検査する | HTML/PDF/DOCXの各出力で実際の成果物を検証する |

**現行との対応**：ディレクトリのsource目録 #620、資料間明示ID照合 #626、Excel併用執筆 #514、実務価値観測 #524、HTML分解 #553、納品PDF/Word #635〜#637、改訂 #638、図表と相互参照 #639。これらがDocument Graphや成果物全体検収を既に実装・受理したという意味ではない。

## 4. どの時点でも納品可能であるための条件

**編集中の内容が常に整合していること**ではなく、**最後に検収した納品可能版を原本と依存資産ごと再現できること**を基本の仮説とする。

必要な条件の候補は、版／digestで固定した入力、原本／変換物／参照先を含む収録範囲、最終成果物、検査条件・結果、変更時の失効／再確認、人による意味と納品範囲の受理である。単なる参照一覧やsource digestだけでは、実ファイルの保全・再現・完全性を保証しない。

検証の水準は少なくとも**参照・集合の形式的整合**、**内容・見た目の同等性**、**契約や業務要件への適合**を分ける。人の受理済み意味を、AIの高い類似度や一部の合成試験から推定しない。

## 5. Obsidian等との境界

Obsidian等のMarkdown編集・リンク・バックリンク・Outline・Graph・Canvas・一覧UIは、設計上の参考および将来の連携候補とする。しかし、MMIの主目的は汎用ノート編集ではなく、**既存の多形式文書体系の出典・依存・再構成・納品品質**の検証にある。

MMIの `![[...]]` はObsidianの類似記法と意味が異なる場合がある。特に `#`、`|`、問い合わせパラメータを含むMMI記法の読込み／保存／往復時の保持を実測するまでは、互換と断定しない。Obsidianを正本や必須Hostとせず、複製・独自APIの導入も先行させない。

## 6. SIer企業のセキュリティ・配布

VS Code拡張が既に承認された開発環境で導入しやすい場合と、署名されたDesktopアプリを中央配布する方が承認しやすい場合がある。**形式だけで一律に優劣を断定しない**。

少なくとも、Workspace外参照／リンク・symlink／ファイル置換、原本非改変、ネットワーク送信、外部AIへの情報受渡し、ファイル実行・マクロ・HTMLスクリプトの隔離、ログとcacheの機密保持、依存物・更新・署名を評価対象とする。AI連携は既存方針どおり外部へ自動送信しない。

## 7. 将来のTEI＋Wails製品と引渡し

TEI側の[Studio PoC #1824](https://github.com/hat47x/tei-platform/issues/1824)にはWailsでのWeb/Desktop共通操作の試作がある。一方、正式な製品Plugin／Host Authority／Workspace許可／Windows実GUI／配布署名について、MMIが利用可能な完成済み基盤であるとは判断しない。TEIの[ADR-0032](https://github.com/hat47x/tei-platform/blob/main/plan/adr/0032-composition-kernel-replacement.md)・[ADR-0033](https://github.com/hat47x/tei-platform/blob/main/plan/adr/0033-core-and-plugin-subprojects.md)は目標構成と実装証拠を分ける。

本流製品へ引き渡すのは、利用シナリオ、必要な情報単位と参照関係、失敗ケース、受入条件、生成AI協働で役立つ情報、実測値、テスト素材、選択的に再利用可能なコードである。**MMIの内部実装・VS Code UI・名称を全面継承する必要はない。**

TEIのDesktopアプリにMMIを組み込む試験は、将来の本流製品を即時実装することとは別。必要な基盤の成熟を判断した後に、Wails製品固有の開発課題として扱う。

## 8. 当面の実務上の進め方

1. [#658](https://github.com/hat47x/markdown-matrix-injector/issues/658)の単一Markdown／複数Excelという小さいPoCから開始し、#620の目録経路との重複を確認する。
2. 原本の完全性、納品対象の識別、参照・未解析範囲を検査し、実務の障害と誤認を記録する。
3. 既存の取り込み・provenance・detach経路を使い、少数の表・画像・本文で段階的再構成を試す。
4. #524の実利用観測へ渡し、「全体を把握しやすくなったか」「情報漏れや手戻りを検出できたか」「AIによる横断レビューの根拠が明確になったか」を比較する。
5. 必要性が具体的に現れた機能のみ既存Issueと照合し、MMIで実装するか将来製品へ持ち越すかを判断する。

本書は計画・構想の整理である。コード変更、Issueの完了、PoCの試験合格、将来製品の機能実装、正式な受入を意味しない。
