## 対象と起票根拠

同じ画面のコメント規則を二箇所で比べる際、条件差、条件不足、同じ条件での値の相違を分け、次に確認する条件を一問にする研究候補である。説明例で入出力は定義できたが、手動の意味対応と条件集合を準備する負担を上回る執筆上の効果は未確認のため、実装採用を保留する。

[既存・新規のExcel表を使う併用執筆](issue-0211-vscode-excel-coauthoring-flow.md)を先に進める。本件をOpenへ戻すには、通常の参照・Markdown追記・レビューで不足する実際の仕事を示し、同じ資料で修正できた記述と追加の準備を比べる。以下の比較設計は採用後の候補であり、専用CLI作業票を先行実装する指示ではない。

ジャイナ由来の条件付き叙述から適用範囲を保持し、Llull由来の交差から重なりを調べ、stasis・ニヤーヤから問いと適用の不足を分ける。これはMMI向けの設計上の操作であり、各体系による意味の自動判定ではない。

## 入出力と最初の境界

利用者が二つの引用、引用元の相対位置、同じ比較枠として扱う対象・性質・画面・役割・版・用語定義を指定する。既知の軸だけを指定でき、未確認はそのまま残す。最初に計算する軸は「操作」一つに限る。比較枠が未確認または異なる場合は、値の相違を確定せず理由を出す。

操作条件は、人が列挙した有限の操作集合に対する明示集合と、未記載を分ける。「全操作」はその比較枠の集合を明示的に選んだ場合だけ扱い、未記載を全操作へ補わない。集合の重なりを計算する部分は決定論的とし、集合や意味を指定した人の注釈と分ける。

原本引用、手動の意味対応、適用範囲の交差、値の一致・相違、優先関係の未確認、次の問いをMarkdownの下書きへ出す。相違が残る場合もどちらかを正しい規則として自動採用しない。例外の優先関係は記録できても、初期実装では規則の自動解決に使わない。

最初の引用入力は、人が選んだworkspace内のMarkdown箇所に限る。引用文字列と選択位置を現在sourceに照合し、同じ文字列が別箇所にあるだけでは結び付けない。既存Candidateを関連付ける場合はそのlocator・fingerprintを参照し、引用用に新しいCandidate kindを作らない。引用検証が通ったことは、意味対応の正しさを保証しない。

利用経路は未決定とする。VS Codeで比較中の箇所を明示選択する操作と、別作業票を準備する操作を比べ、通常の執筆から離れる負担を先に確認する。採用する場合も同じApplication処理を使い、source書換え、採否の自動変更、文中からの条件自動抽出、外部送信は追加しない。

## 採用を判断してからの実装候補

1. 作業票の入力例と下表の期待出力を固定する。比較枠、引用の照合、未記載、明示的な全操作、優先関係の未確認を表せる最小の内部型を決める。
2. CoreにI/Oを持たない範囲比較を置く。Applicationがsource照合、作業票の読込み、問いの選択、Markdown出力を担当する。問いは未決の理由と、その答えで変わる判断を一組だけ出し、人が変更・保留できるようにする。
3. 明示的なローカル利用経路へ接続する。通常描画・診断・レビュー採否は変更しない。製品CLIへ公開する場合はhelp・入力検証・終了状態・文書を同時に揃える。
4. 同じ資料の通常レビューと下書きを使い、読解・記述の差と準備の負担を確認する。実務上役立つ範囲へ調整してから完了を判断する。

## Acceptance criteria

- [ ] 引用の照合と、人が付けた意味・条件の注釈を出力上で分ける。source変更や引用位置の不一致は再選択を求め、古い引用を確認済みと表示しない。
- [ ] 未記載を全操作と区別し、明示集合が同じかだけでなく、その交差を比較する。全操作の意味は人が指定した有限の比較枠へ限定する。
- [ ] 条件差・条件不足・交差部分の値の相違・優先関係未確認を保持する。例外や許可を無記載から補わず、正しい規則を自動決定しない。
- [ ] 未決理由から次の一問と、答えで変わる判断を出す。人が問い・条件を修正し、保留して通常の執筆へ戻れる。
- [ ] Core・Application・ローカル入口で同じ入力に同じ比較結果を返す。意味注釈を`observed`へ昇格せず、Candidate・ledger・reviewの状態を変えない。
- [ ] 利用者が同じ材料で適用条件を説明し、比較下書きを修正できることを確認する。通常レビューから改善した記述・不要な準備・残る誤読を記録し、有用度の判断を残す。

## Validation plan

以下は実装後に用いる作例であり、今回の製品テスト結果ではない。Aは差戻し時必須、Bは承認時任意、Cは操作未記載で任意、Dは差戻し時任意とする。Aの着想元だけが基本設計書キットで、追加記載は作例として作る。

| ケース | 期待する結果 |
| --- | --- |
| A / B | 適用操作が重ならず、同条件の値の相違にはしない |
| A / C | Cの操作が未確認で、適用範囲を確かめる問いを出す |
| A / D | 差戻しで値が相違することを残す |
| A / 全操作で任意 | 範囲が異なっても差戻しで重なる。相違候補を落とさない |
| A / 全操作で必須 | 差戻しの値は一致するが、適用範囲は同一としない |
| A / 全操作の任意、明示的な例外関係あり | 例外関係を残す。自動で勝者を選ばず、業務上の優先が確認済みかを示す |
| Aだけ | 承認時の任意・必須・禁止を補完しない |
| 版・対象・定義が未確認 | 値の比較より先に、比較枠の不足を示す |
| 引用位置不一致、source差替え | 引用を再選択する。類似箇所への自動再束縛はしない |

単体では範囲と未記載の扱い、結合ではsource照合・Markdown出力・入口との一致を確認する。既存の描画・診断・reviewに影響しないことも対象経路で確認する。予定するテスト名は`conditionBoundComparison.test.ts`と`conditionBoundComparisonDraft.test.ts`であり、現時点では未作成である。実装時に開発環境の手順で関連テストを実行する。

実機では入力から下書き表示、条件修正、保留までを確認する。利用価値は、同じ材料を読んだ人の説明と修正成果物、準備にかかった手間から判断し、自動テストや問いの件数で代用しない。

## Remaining work

最初の作業は、通常レビューでは直せなかった具体的な記述と、比較入力の準備負担を示すこと。有用な範囲が確認できるまで内部型・新コマンド・作業票schemaを実装しない。実装・自動テスト・製品実機・利用価値の確認は未着手である。
