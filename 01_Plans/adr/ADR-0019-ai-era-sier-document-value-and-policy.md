# ADR-0019: 生成AI時代のSIer設計文書に向けた製品価値とプロジェクト方針

- Status: Proposed
- Date: 2026-09-27
- Deciders: Human Sponsor（採否）、MMI Lead Agent（起案）
- Scope: 製品価値、利用者と利用経路、中核概念、優先度、評価方法
- Related: [ADR-0012](ADR-0012-mission-redefinition-notation-as-governance-boundary.md)（使命）、[ADR-0016](ADR-0016-notation-first-input-assistance.md)（入力支援）、[ADR-0017 Windowsクリップボード](ADR-0017-windows-clipboard-provenance-bridge.md)、[ADR-0017 Fly-inspired書式補助](ADR-0017-fly-inspired-format-deviation-assistance.md)、[ADR-0018](ADR-0018-cognitive-assistance-plane.md)（認知補助の境界）、[製品要求](../../00_Prompt/requirements.md)

## 背景

### 設計書の書き方が変わった

SIerの設計書作成では、本文の起案をAIエージェント（Claude Code、GitHub Copilot、Codexなど）に任せる運用が現実になった。本文は速く書けるようになったが、次の失敗が増える。

| 失敗 | 設計書での現れ方 |
| --- | --- |
| 表の転記誤り・値の捏造 | 権限表の○×、コード値、項目の桁数が正本と違う |
| 存在しないIDの記述 | 本文に要件IDやメッセージIDを創作する |
| 正本の更新への追従漏れ | Excelを直したが、写した表が古いまま残る |
| コンテキストに入らない正本 | 数千行のExcelを読ませると、要約や欠落が起きる |
| 照合の負担 | レビュアーが表とExcelを1セルずつ突き合わせる |
| 根拠の説明 | 納品版がどの正本から作られたかを示せない |

AIが速く書くほど、これらの失敗も速く大量に起きる。本文はAIが生成できるが、**表の値が正本どおりであることは生成では保証できない。** ADR-0012が定めた「宣言的・読み取り専用・検証可能な参照」は、まさにこの保証を与える。

### 人による執筆・レビューと、既存文書の取り込みは残る

SIer案件では、顧客との合意、レビュー、承認を人が行う。AIが起案しても、人が直接書き、読み、直す作業はなくならない。

既存の設計書（Excel方眼紙の設計書、Wordの仕様書）をMarkdownへ移すときは、判断がさらに人に寄る。どの表を正本として残し、どこを本文へ移し、どこを取り込まずに置くかは、案件の事情、顧客との取り決め、文書の読まれ方に左右される。AIに一括変換させても、この判断と確認は人に残る。

### 現在のMMIはAIから使いにくい

- 参照・診断・描画・納品一覧の機能はVS Codeの画面操作でしか使えない。AIエージェントはシェルとファイルで作業するが、呼び出せる入口は開発用の[render-document.ts](../../03_Implement/scripts/render-document.ts)だけである。
- 記法と作法をAIに教える利用者向けの指示ファイルがない。本リポジトリのAGENTS.mdはMMIの開発者向けである。
- [実務サンプル](../../04_Documentation/samples/practical/README.md)は12本あるが、基本設計書・テーブル定義書・試験仕様書といったSIer成果物の型としては提供していない。

### 研究層の成果がまだ利用者に届いていない

`src/experimental`の研究は、既存文書の取り込みと人のレビューを支える能力を育てている。

- 既知の書式に一致するか、曖昧か、新しい書式かの判定（worksheet format）
- 表らしい領域と、表でない領域（連絡先カード、箇条書き、縦に積んだ項目の組）の区別、見出しの境界の推定（structured artifact）
- 注意して見るべきシートを示すレビュー経路の判断（review route。承認の判定ではない）

2026-09-27時点のリポジトリを実測すると、研究層は70ファイル・約19,500行で、製品のソース（49ファイル・約8,800行）より大きい。単体テスト122ファイルのうち86ファイルが研究層を読み込む。2026-09-18以降の非マージコミット134件のうち、74件が研究層に触れた。

一方、研究層は製品コードから読み込まれておらず、VS Codeの利用者が使える機能にはなっていない。利用者による価値確認の記録もない。問題は研究の要否ではなく、**成果を利用者の操作へつなぐ作業の優先度**にある。

## 決定

本ADRは既存の境界（読み取り専用、containment、決定論、MMI Notation v1の凍結、認知補助は権威を持たないとするADR-0018）と、既存の対象範囲を変更しない。新たな対象外は設けない。以下は価値の定義と、作業の優先度である。

### D1. 製品価値

> **AIが書いても、人が書いても、表は正本どおり。**
>
> MMIは、Excel・CSVの正本から必要な表だけを、写さずに参照するための規約とツールである。AIエージェントはコマンドで、人はVS Codeで参照を書く。MMIは正本から表を描き、参照が正しいかを機械的に検証する。既存の設計書を取り込むときは、表の領域や書式の候補を示して人の判断を助ける。レビューは本文と参照の宣言に集中できる。

担い手ごとに主に担うことを次のように整理する。

| 担い手 | 主に担うこと |
| --- | --- |
| AIエージェント（利用者が選ぶ） | 本文の起案、正本の構造の理解、参照の作成、検証結果に基づく修正 |
| 人（VS Code） | 執筆とレビュー、既存文書から何を取り込むかの判断、候補の採否、確定の承認 |
| MMIの決定論的コア（Authority Plane） | 正本の目録、参照の検証、描画、納品物と根拠の記録 |
| MMIの認知補助（Cognitive Assistance Plane） | 書式・表の領域・注意点の候補と説明。人の判断を助け、決定はしない |

表の値は転記せず、正本から描く。どの担い手でも同じである。

### D2. 2つの利用経路

同じエンジンと同じ保証を、2つの経路から使えるようにする。

| 経路 | 使う場面 | 入口 | 主な能力 |
| --- | --- | --- | --- |
| A: AIエージェント経路 | 新しい文書の起案、章の追加、正本の更新への追従 | CLI、AI向け指示パック | 目録、検証、展開、確定版 |
| B: 人の手動編集経路 | 執筆、レビュー、既存文書の取り込み | VS Code拡張 | プレビュー、貼り付け、補完、案内付きの作成、説明からの検索、診断、認知補助の候補 |

経路Aで`inspect`が示す表の候補に、研究層の領域判定を候補として添えることもできる。候補は非権威であり、ADR-0018に従う。

### D3. 利用者が得るもの

| 利用者 | 得るもの |
| --- | --- |
| 設計者（SE） | 「この正本を参照して◯章を書いて」とAIに頼むだけで、表の転記と更新の作業がなくなる。自分で書くときもVS Code上で参照を作り、その場で結果を確かめられる |
| 既存文書を移行する担当者 | 既存のExcel設計書から、表の領域、既知の書式、注意が必要な箇所の候補を示され、何を参照にし何を本文へ移すかを判断できる |
| AIエージェント | 巨大な正本を読まずに構造を知り（目録）、自分が書いた参照を安定した診断コードで検証して直せる |
| レビュアー・PM・品質保証 | 表の照合が不要になり、正本の変更が及ぶ範囲を一覧で確認できる |
| 顧客・監査 | 納品版がどの時点の正本から作られたかを確認できる |
| 判断を記録する人・組織 | 判断の根拠にした表を、ファイル・シート・範囲と正本のダイジェストの組で残せる。後から、当時と同じ表かを確かめられ、正本が変わっていれば気づける |
| 情報システム・セキュリティ | 書き込み・ネットワーク・ワークスペース外への参照がない経路を、人にもAIにも渡せる |
| 組織（事業部・PMO） | 成果物の型（文書キット）と正本の型を標準として配り、AI活用と手作業の品質をそろえられる |

設計判断、変更要求の判定、レビューへの回答などの記録は、記録する側が持つ。MMIが渡すのは、どの表のどの断面を見たかという参照と、そのときの正本のダイジェストまでである。判断を記録する別のシステム（たとえば兄弟製品のSEI）から使われる場合も、MMIは読み取り専用のままで、どちらの製品も相手なしで成り立つ。使い方は[記法仕様の付録](../../04_Documentation/spec/mmi-notation-v1.md#付録-外部の判断記録で根拠を固定する非規範)、SEIの語彙との対応は[SEIの判断の意味論との対応](../../02_Architecture/sei-decision-semantics-mapping.md)、進め方は[issue-0192](../issues/issue-0192-sei-decision-basis-table-binding.md)に記す。

### D4. SIer品質とMMIの保証

SIer品質を7つの要素で捉え、MMIが担う保証を対応させる。

| 品質の要素 | MMIの保証 | 状態 |
| --- | --- | --- |
| 正確性 | 表は正本から決定論的に描画し、値を生成しない | 実装済み |
| 文書間の整合 | 複数の文書が同じ正本を参照するため、構造的に一致する | 実装済み |
| 検証可能性 | 参照を安定した診断コードで機械検証する。同じ入力から同じ結果を得る | 実装済み（VS Code内のみ） |
| 変更管理 | 正本の変更が影響する文書・章を列挙し、確定版との表の差分をテキストで示す | 未実装 |
| 追跡可能性 | どの文書がどの正本のどの断面を参照しているかを台帳にする | 未実装 |
| 納品体裁 | 改ページ・用紙の向き・別紙・納品物一覧。PDF・Wordへの変換は既存の変換器を使う | 一部実装（PDFはWeasyPrint経路のみ確認） |
| 統制 | 読み取り専用、ワークスペース内に限定、ネットワーク取得なし | 実装済み・仕様化済み |

現時点の保証は、表の値と参照の正しさまでである。本文の主張（「承認できるのは管理者のみ」など）と表の整合は、展開結果を読んだAIと人が確認する。この確認を助ける機能は、D9の候補として扱う。

### D5. 中核概念

| 概念 | 意味 | 使う既存資産 |
| --- | --- | --- |
| 正本 | 一覧データの唯一の置き場 | ― |
| 参照 | 写さずに指す。宣言的・読み取り専用・決定論的 | MMI Notation v1 |
| 断面 | 必要な範囲・列・行だけを見せ、読者とAIのコンテキストを節約する | 変換パイプライン |
| 目録 | 正本のシート、表の位置、見出し、行数の地図。正本を丸読みせずに参照を書ける | 補完の表検出、研究層の領域判定 |
| 取り込み | 既存文書から、正本として残す表と本文へ移す内容を人が判断する作業 | 貼り付け・内容照合、研究層の書式認識・領域判定・レビュー経路 |
| 検証 | 参照を機械検証し、AIの自己修正、人の執筆、CIの関門に使う | 診断・修正候補 |
| 展開 | 参照を標準のMarkdown表またはHTMLへ置き換えた出力。読み戻し、PDF・Wordへの変換、他ツールの入力になる | プレビューの描画、render-document.ts |
| 参照台帳 | 文書・行・正本・シート・範囲・条件の一覧。影響分析と追跡の基礎 | パーサー（新規は集約のみ） |
| 確定版 | レビュー・納品時点の展開結果と正本のダイジェスト。次の版との差分の基準 | 納品物一覧 |
| 文書キット | SIer成果物ごとの章立て、正本の型、AIへの依頼例、検証手順 | 実務サンプル |

### D6. 標準の作業ループ

**経路A（AIエージェント）:** 利用者がAIに依頼し、AIが次の順で作業する。

1. **目録を見る:** `mmi inspect <正本>`でシート、表、見出しを確認する。
2. **参照を書く:** 本文を起案し、表は`![[...]]`で参照する。
3. **検証する:** `mmi check <文書>`の診断に従い、エラーがなくなるまで直す。
4. **読み戻す:** `mmi render <文書>`で展開結果を読み、本文の主張と表が矛盾しないか確かめる。
5. **人がレビューし、確定する:** 本文と参照の差分、展開結果を確認し、確定版を残してPDF・Wordへ変換する。

利用者の依頼は、たとえば次の程度で足りるようにする。

```text
masters/権限マトリクス.xlsx を正本として、docs/基本設計書.md の「4. 権限設計」を書いてください。
表は写さずにMMIで参照し、mmi check が通るまで直してください。
```

コマンド名は案であり、CLIの設計で確定する。

**経路B（人・VS Code）:** 既存文書の取り込みでは、次の流れを支える。

1. 既存のExcel設計書を開き、MMIが表の領域・既知の書式・注意が必要な箇所を候補として示す。
2. 人が、参照にする表、本文へ移す内容、取り込まない部分を決める。
3. 選んだ表を参照として挿入し（貼り付け、案内付きの作成、説明からの検索）、プレビューで確かめる。
4. 診断に従って直し、レビューへ回す。

### D7. 優先度

上から順に作業を割り当てる。これは順序であり、下位の作業を禁止したり打ち切ったりするものではない。手が空いた範囲で並行して進めてよい。

**優先度1: 経路Aの最小経路**

既存モジュールの配線が中心で費用が小さく、現状との差が最も大きいため先に置く。

- **CLI:** `inspect`・`check`・`render`・`manifest`。既存の診断・表検出・描画・納品物一覧を、VS Codeに依存しない入口から呼ぶ。出力は人向けの短い表示と、AI・CI向けのJSONの2種類。`check`は結果を終了コードでも返す。`inspect`は既定で構造だけを返し、セル値は明示したときに限り先頭の数行を返す。`inspect`と`render`の出力は利用者のAIの提供元へ送られ得るため、何を渡してよいかは利用者の組織の規則に従うと明記する。
- **AI向け指示パック:** 記法、作業ループ、注意事項（表を転記しない、正本を編集しない、記法で表せない依頼を別の意味へ言い換えない）を1ファイルで教える。Claude Codeのスキル、`AGENTS.md`、`.github/copilot-instructions.md`へそのまま置ける形で配布する。
- **文書キット1本:** 基本設計書（機能一覧、画面項目、権限、状態遷移、メッセージ）。既存の実務サンプルを組み替えて作る。
- **AI執筆ベンチマーク v0:** D9の課題を5件以上。
- **到達の目安:** 汎用AIエージェントに依頼文と指示パックだけを渡し、キットの章を参照付きで完成させ、`check`のエラーが0件になることを実環境で確かめる。この経路でVS Codeを必須にしない。

**優先度2: 経路Bで研究の成果を利用者に届ける**

既存文書の取り込みは、実案件で使い始めるときの最初の関門であり、人の判断が最も必要な場面であるため、次に置く。

- 研究層の書式認識・領域判定・レビュー経路のうち、既存Excel設計書の取り込みに効くものから、VS Codeで候補として見える操作へつなぐ。候補の表示、採否、参照としての挿入までを一続きにする。
- 研究層の中では、利用者の操作と観測に届く作業を、内部の評価基盤の拡充より先に行う。
- 既存の入力支援（issue-0110・0111・0114・0115）の残作業（多環境での実機確認、利用者の観測、説明からの検索の言い換え対応）も、この優先度で進める。
- **到達の目安:** 既存のExcel設計書を題材に、人が候補を見て取り込み範囲を決め、参照付きの文書にできることを実機で観測する。

**優先度3: SIer品質の保証**

- **参照台帳と影響分析:** 全文書の参照一覧と、指定した正本（またはgitで変更された正本）を参照する文書・章の一覧。CLIとVS Codeの両方から使う。
- **確定版と差分:** 展開結果と正本のダイジェストを記録し、前の確定版との表の差分をテキストで示す。Excelのバイナリ差分をレビューできるようにする。
- **CIの関門:** GitHub Actionsなどで`check`を実行する手順と例。
- **納品の手順:** 展開済みMarkdownからPandocでWord、HTMLからPDFへ変換する手順。確認した変換器・版・制約を明記する。
- **到達の目安:** 正本を1か所変えたとき、影響する文書・章と表の差分を、人手で探さずに示せる。

**優先度4: 組織への展開**

- 文書キットの追加（テーブル定義書、IF定義書、試験仕様書・試験成績書、運用手順書、移行計画書）。
- D9の候補のうち、効果を確かめたものの追加。
- 社内標準へ組み込むための導入手順（テンプレートの配布、正本の置き場と命名、レビューの規則）。

新しい能力はまずエンジンへ置き、CLIとVS Code拡張の両方から同じエンジンを呼ぶ。経路ごとに別の実装を作らない。

### D8. 当面の優先度が低いもの

次は対象から外すのではなく、既存の手段で当面は代替できるため優先度を下げる。必要性が観測されたら、D9の方法で優先度を見直す。

- 集計・計算: 正本側（Excelの数式や集計シート）で計算し、結果のセルを参照すれば代替できる。
- Word・PDFの独自生成: 展開結果を既存の変換器へ渡せば代替できる。
- MMIに組み込むLLM: 経路Aでは利用者のAIが担う。ローカルLLMの評価は、製品要求どおり保留を続ける。

### D9. 探索の方法と優先度の判断

必要な機能を確実に見つけるため、次の3つを優先度の判断材料にする。着手を許可制にするものではない。

**仮説カード:** 新しい機能や研究について、次を1枚に書いて比較する。

1. 対象の成果物と利用者、使う経路（A・B・両方）
2. 現在起きている失敗（背景の表のどれか、または新しい失敗）
3. MMIでの解決方法と、既存の手段で代替できない理由
4. 既存の境界との整合
5. 効果を測るベンチマーク課題、または利用者の観測方法
6. 効果がないと判断できる条件

**AI執筆ベンチマーク（経路A）:** 既存の実務サンプル（架空の申請・承認システム）を題材に、依頼文だけをAIへ渡す課題を用意する。同じ課題を「MMIなし（表を写す）」と「MMIあり」で実行し、次を記録する。

- 正本と一致しない表のセル数、存在しないIDの数
- `check`の結果だけで解消できた参照エラーの割合
- 正本を変えた後の追従漏れ
- 依頼から完成までの往復数、人手による修正の回数

**取り込みとレビューの観測（経路B）:** 既存のExcel設計書（架空、または匿名化した実例）を題材に、人が取り込み・レビューする様子を記録する。

- 候補を採用・修正・却下した割合と理由
- 取り込み範囲を決めるまでの時間
- 注意が必要と示した箇所で、実際に指摘が見つかった割合

結果は、使ったAIや題材の種類・版・日付とともに記録する。AIの出力は揺れるため、1回の成功を保証として扱わない。自動テスト、実機確認、ベンチマーク、利用者による価値確認を区別して報告する。

今後の候補の例:

- 本文中のID（REQ-、MSG-など）が正本に実在するかの確認
- 本文の主張と表の整合確認の支援（認知補助の候補として）
- 前の確定版との差分を、文書内の変更箇所として示す表示
- 用語集・コード定義との表記の整合確認
- CLIを包むMCPサーバー

### D10. 指標

ADR-0012 D6の指標を、2つの経路に合わせて次のように具体化する。

1. 正本と一致しない表のセル数（MMIで参照した表は0。写した場合との差を示す）
2. AIが検証結果だけで参照エラーを解消できた割合
3. 依頼から`check`の通過までの往復数
4. 既存文書の取り込みで、候補がそのまま、または修正して採用された割合と、取り込みにかかる時間
5. 正本の変更時に影響を特定するまでの時間と、追従漏れの件数
6. レビューで表の照合に使う時間
7. 利用者による価値確認を済ませたシナリオの数

## 受け入れるトレードオフ

- 2つの経路を並行して育てるため、能力をエンジンへ集める規律を守らないと二重実装になる。
- CLIを加えると、配布形態（npm、単体の実行ファイル、拡張への同梱）の判断と保守が増える。
- 研究層の保守（テスト86ファイルを含む）を続ける。その費用は、成果を利用者の操作へつなぐことで回収する。
- 保証の範囲は表の値と参照まで。本文との整合は確認の支援として扱い、保証とは区別する。
