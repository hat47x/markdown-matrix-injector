## 背景

### レガシー文書は一括移行できない

SIerの設計資産には、Excel方眼紙、画面ダンプを貼ったExcel、Word、CSV、XML、JSON、独自テキストなどが長期間残る。Excel方眼紙の文書をレガシーとみなす見方と、その書き方に合理性があるとする見方の両方に理由がある。MMIは両者の橋になる（D0）。これらには表だけでなく、画像、AutoShape、選択肢、階層・ツリー、箇条書き、注記、リンク、図形同士の関係、セル配置に暗黙化された意味が含まれる。

全面的な一括変換は、情報落ちとレビュー負担が大きい。一方で、旧文書を永久に人手で参照し続ける運用も、AIエージェントから扱いにくく、二重管理と転記ミスを残す。

必要なのは「レガシー文書を今すぐ捨てる」ことではなく、**人が慣れた道具と書き方を保ったまま段階的にモダナイズし、いつ切り離しても困らない状態へ近づけること**である。移行の速さより、人が作業の手を止めないことを優先する（D13）。

### 生成AIには、読めることより安全に使えることが必要

AIエージェントはExcelや文書を直接読めるようになったが、巨大ファイルの丸読み、暗黙構造の見落とし、転記、存在しないIDの生成、更新追従漏れは依然として起こる。AIが高性能になっても、出典、再現性、読み取り専用、構造の確定と推定の区別は外部の契約として必要である。

MMIが提供すべき価値は、AIそのものになることではない。**AIと人がレガシー資産を安全に理解し、必要な構造だけを近代的な文書へ移し、機械的に検証できる境界を提供すること**である。

### 軽量認知の役割

既存のstructured artifact、worksheet format、CPU範囲探索の研究では、汎用LLMへ全面委譲しなくても、表らしい領域、既知書式、曖昧性、候補範囲をローカルCPUで絞れることを確認してきた。

この能力は表検索だけに閉じず、レガシー文書の暗黙構造を「候補」として発見する軽量認知へ一般化する価値がある。ただしADR-0018どおり、認知結果は権威にならない。明示構造、推定構造、人が確認した構造を区別する。

## 決定

### D0. 2つの見方の橋になる

Excel方眼紙の設計書には、2つの見方がある。MMIはどちらも否定せず、**両者の尊厳を保つ橋**として働く。

**既存のスタイルには合理性がある。** Excel方眼紙での文書作成は、合理性の帰結であり、現代でも有効な方式である。

- オフィスの座席表をExcel方眼紙で作るのは、公開の範囲と編集のしやすさを考えれば十分に合理的である。
- 設計書でも、図表で設計情報を整理することはエンジニアリングそのものである。罫線、セル結合、AutoShape、貼り付けた画面ダンプを併用する書き方は、人が考えながら最速で書ける形である。
- 図表の内容が正規化されず、開発の自動化に使われないことは従来の課題だった。生成AIによるコーディングの自動化でその穴は埋まりつつある。
- Gitで差分を取りにくい、Webで公開しにくいといった点は、文書の編集・流通の様式の違いであり、代替手段や理由がある。

**レガシーとみなす見方にも、もっともな理由がある。** Excel方眼紙の文書をレガシーと感じる気持ちはよく分かる。SIerの合理性から顧客納品物として固定されてきたOffice文書・Excel形式の位置付けは、生成AIの発展によって徐々に揺らいでいる。意味がセルの位置・結合・図形の配置に埋め込まれた文書は、MarkdownやHTMLに比べて、AIが構造を取り違えず、全体を丸読みせずに、出典を保って扱うことがまだ難しい。AIの側も対応を強めているが、この点は**生成AIとの協業を妨げる**現実の課題である。

MMIは、どちらかの側へ人を移すことを目的にしない。Excelで書き続ける人は書き方を変えずにAIと協業でき、MarkdownやHTMLへ移りたい人は、Excelに残る資産を失わずに移れる。どちらを選んでも、相手の側の文書と同じ情報を共有できることを目指す。

Excel設計書の第一の利用場面は、既存設計書の書式と運用を踏襲し、Excelを更新しながらMarkdown文書と共存させることである。新しい表を人がExcelで作成することも継続的な利用として支える。MMIの読み取り専用という境界は、人による原本の作成・更新を制限しない。

したがってMMIの役割は、方眼紙の設計書を作り変えさせることでも、移行を止めることでもなく、**人が書いたExcelを、そのままAIと協業でき、望めばMarkdownへ移せる形にすること**である。

- 表や範囲は、構造を読み取って参照・取り込みできるようにする。
- 図形・画面ダンプ・レイアウトそのものに意味があるシートや範囲は、**そのまま画像として取り込む**ことを正当な取り込み方とする（Candidate種別 `Sheet / Region snapshot`）。描いた人の見た目と意図を、そのまま文書へ運べる。描画の方式はD14に従い、CIで再現できる方式を優先する。
- 読み取った構造と画像に出典を付け、AIが原本を丸読みせずに扱えるようにする。

### D1. 製品価値

> **人は慣れた道具で書き続けられ、その内容はMarkdown文書、AI、機械と共有できる。移行する範囲とペースは人が決め、必要な範囲ではMMIからも離れられる。**
>
> MMIは、業務文書・構造化データから再利用可能な情報単位と関係を読み取り専用で取り出し、既存・新規の原本とMarkdownを併用しながら、望む範囲を段階的に移行できるモダナイズ基盤である。
>
> 表、画像、図形、ツリー、リストなどを候補として抽出し、軽量な認知支援で暗黙構造を見つける。確定した構造は決定論的なAuthority Planeで検証・参照・展開する。元文書を正本または根拠として保持し続けられ、廃止すると人が決めた範囲では標準的なMarkdown・画像・構造化データへ実体化して、元文書やMMIを外しても成果物が成立する経路を持つ。

既存の「AIが書いても、人が書いても、表は正本どおり」は重要なユースケースとして残すが、製品価値全体を表参照へ限定しない。

### D2. モダナイズは3状態を扱う

MMIは一括置換ではなく、同じプロジェクト内で次の状態を混在可能にする。

| 状態 | 意味 | 主な用途 |
| --- | --- | --- |
| Linked | 原本（人が書き続けるExcel等）を残し、必要な断面を参照する | 既存MMI記法、変更追従、二重管理の抑制。Excelで書き続ける場合の恒久的な形 |
| Extracted | 原本から表・画像・ツリー等を標準資産へ取り込み、出典と対応を残す | Markdown化、assets化、段階移行 |
| Detached | 必要情報が標準資産へ実体化され、原本をアーカイブ・削除しても文書が成立する | 原本の廃止を人が決めた範囲の長期保守 |

プロジェクト全体を一度にDetachedへ移す必要はない。シート、範囲、画像、章などの単位で段階移行できることを重視する。

**3状態は順に進むべき段階ではなく、情報単位ごとに選ぶ状態である。** 人がExcelで書き続ける情報はLinkedのままでよい。Detachedは、原本を廃止すると決めた範囲で使う。Detachedへ移した割合の大きさを、それだけで成功とみなさない。

### D3. 「いつでも切り離せる」を製品要件にする

ロックインを避けること自体を価値とする。MMI固有機能を利用していても、最終的に次を出力できることを目標とする。

- 標準Markdown
- 通常の画像・添付ファイル
- JSON / YAML / CSV等の一般的な構造化データ
- 出典・変換条件・ダイジェストを記した可読なmanifest
- MMI記法を展開済みにしたmaterialized文書

将来の `detach check` は、未展開参照、未取込資産、原本にしか残っていない必須情報、壊れたリンクを列挙し、「原本を外しても成立するか」を機械的に確認する。

**MMIを使い続けることを成功条件にしない。安全にMMIを外せることも成功条件とする。** ただし離脱は選択肢として保証するものであり、人に移行を急がせる圧力にしない。

### D4. Source AdapterとSemantic Candidateを中核概念にする

入力形式とMarkdown出力を直接1対1で結ばない。

```text
Legacy / Structured Sources
        ↓
Source Adapter
        ↓
Observed Structure
        ↓
Candidate Detection / Structuralizer
        ↓
Semantic Candidate Graph
        ↓
Confirm / Reference / Extract
        ↓
Markdown / assets / structured data
```

初期のCandidate種別は次を想定する。

- Table / Range
- Image / Screenshot
- Sheet / Region snapshot（図形・レイアウトに意味があるシートや範囲を、そのまま画像として取り込む。D0）
- Shape / Text box
- Diagram / connected shapes
- Tree / hierarchy
- Choice list / list
- Note / comment
- Link
- Section / heading structure

候補型はExcelオブジェクト型と同一視しない。たとえばTreeは、JSON/XMLの明示的ネスト、Excelのインデントや行グループ、番号体系、親列、AutoShape接続、フラットテキストの見出し番号など複数の入力から得られる。

### D5. データソースを表形式へ限定しない

既存のCSV、TSV、Excel、XML Spreadsheet 2003に加え、設計上は次をSource Adapterの候補とする。

- 汎用XML
- JSON / YAML
- インデント・番号・接頭辞などで構造を表したテキスト
- 画像・図形を含むOffice文書
- 将来の他形式

ただし、**対応予定と実装済みを混同しない。** 現行MMI Notation v1の適合範囲は従来どおりであり、新Source AdapterやCandidateは個別の受入条件と検証を通して追加する。

### D6. 明示構造と推定構造を分ける

JSON/XMLの親子関係のように形式自身が持つ構造と、Excel配置やフラットテキストから推定した構造を同じ確度で扱わない。

Candidateは少なくとも次を区別できるようにする。

- `observed`: 原形式に明示された構造
- `inferred`: 規則または認知処理で推定した構造
- `confirmed`: 人または決定論的検証で採用が確定した構造

推定にはmethod、evidence、provider/version、confidenceまたはreason code、provenanceを残し、曖昧な場合はabstainする。認知機能のON/OFFでAuthority Planeの事実を変更しない。

### D7. 軽量認知を「構造発見」の中核能力として育てる

Cognitive Assistance Planeは付加的なAI機能ではなく、レガシー文書の暗黙構造を低コストに候補化する中核能力として扱う。ただし権限はADR-0018のままとする。

優先順は次のとおり。

1. 決定論的parser / metadata / layout規則
2. ローカルCPUで動く疎表現・類似検索・bounded classifier（Fly-inspired、Jev類似技術等）
3. 必要箇所だけを扱うローカルLLM

MMI自身が課金型の外部生成AIサービスを直接呼ぶことは原則としない。汎用LLMを使う場合は、利用者が選んだ外部LLM / AIエージェントからMMIを呼ぶか、MMIが作業依頼と判断材料を生成して利用者側へ渡す。規則で確定できる部分は規則で処理し、曖昧な部分だけを候補化する。

### D8. 取り込み済み資産をプロジェクト単位で追跡する

選択的取り込みでは、同じ画像・表・構造を繰り返し候補に出さないことが実務上重要である。

プロジェクトは、source locator、content fingerprint、candidate type、出力先、参照元、変換条件、確認状態をmanifest/indexとして保持できるようにする。候補表示では少なくとも次を選択可能にする。

- すべて
- 未取込のみ
- 完全一致の取込済みを除外
- 類似候補も含めて確認

fingerprintの方式は候補型ごとに異なってよい。完全一致と類似判定を同じ証拠として扱わない。

### D9. 初回一括変換と継続的な個別取り込みを分ける

モダナイズ開始時には、一括変換が有効な場合がある。既存の変換器を再利用して標準Markdownの土台を作り、その後MMIが候補、出典、重複、構造関係、参照保証を補う構成を許容する。

一方、継続運用では個別取り込みを重視する。

```text
初回:
legacy documents
  → baseline conversion
  → candidate review
  → Markdown + assets + manifest

継続:
legacy source update
  → unimported / changed candidates
  → selective reference or extraction
  → validation
```

特定の一括変換ライブラリを製品価値の前提にはしない。MarkItDown等はAdapterまたは補助変換器として評価できるが、MMI固有の出典・空間関係・候補状態・detachabilityを失わないことを優先する。

### D10. プラグインではなく、共通エンジンを製品の中心にする

VS Code拡張は重要な人間向けクライアントだが、MMIそのものではない。製品の中心を、エディタに依存しないエンジンと契約に置く。

| 提供面 | 役割 |
| --- | --- |
| Core engine / library | Adapter、Candidate、Authority検証、参照、展開、manifest |
| CLI | 人・AI・CIから同じ機能を呼ぶ標準入口 |
| Machine-readable contracts | schema、diagnostic code、manifest、conformance corpus |
| Agent integration | skill / instructions、将来のMCP等。AIが安全にinspect/check/extractできる入口 |
| VS Code extension | 人が候補を確認・採否し、参照・取込・レビューするUI |
| Converter integration | 初回一括変換や外部出力器との接続 |

新能力は原則としてCoreへ実装し、VS Codeだけに閉じた機能を増やさない。

### D11. AIエージェントを第一級利用者とする

AIが巨大な原本を丸読みせず、次の操作を機械的に行えることを目標とする。

1. sourceをinspectして構造と候補を知る
2. 未取込・変更候補を絞る
3. candidateを参照またはextractする
4. 出力をcheckする
5. provenanceとmanifestを確認する
6. detachabilityを検査する

人向け表示とAI/CI向けJSONを同じエンジンから提供する。AIが生成した推測を原本事実へ昇格させず、診断コードとprovenanceで自己修正できるようにする。

### D12. 保証の境界

継続する保証は次のとおりです。

- Read-only: sourceを書き換えない
- Determinism: Authority Planeの同じ入力・設定から同じ結果
- Containment: 許可範囲外を暗黙に読む・送ることをしない
- Visible failure: 非対応・曖昧・不在を隠さない
- Provenance: どこから何を得たかを追跡可能にする
- Abstention: 推定できないものを既知構造へ強制しない

MMIは、文書内容の業務的正しさそのものを自動保証しない。認知支援は候補を示し、決定論的検証と人または利用者が選んだAIによるレビューを組み合わせる。

### D13. 人の作業速度と認知基盤を移行より優先する

モダナイズの過程で、人が作業の手を止めないことを最優先とする。優先順は次のとおり。

1. **人の認知基盤を保つ:** 人が慣れた道具、書き方、見た目、置き場所を変えさせない。ExcelでもMarkdownでも、人が普段どおり書いたものをMMIが読み取る。
2. **作業を止めない:** 人が最速で文書を書ける経路を妨げない。MMIの確認・取り込み・検証は、執筆の後、または執筆と並行して、人の手を待たずに行えるようにする。候補の採否を執筆中に強制しない。
3. **緩やかに移す:** 移行は人が決めた範囲・ペースで進める。一括変換や形式の統一を、利用開始の条件にしない。

VS Codeでは、既存設計書を参照して本文を書く、新しいExcel表を追加する、Excel保存後の表示を確かめる、行列変更に合わせて参照を直すという一連の作業で機能を評価する。解析や意味比較を実装できることだけで、執筆に有用な要件と判断しない。通常の参照操作やMarkdown追記より準備が増える支援は、具体的な効果を確認してから採用する（要求EW01〜EW07）。Coreを共通の技術的中心とするD10は維持する。

この優先順は機能の設計に次のように効く。

- 候補（Candidate）は、人が採否するまで本文を変えない。未確認の候補が溜まっても、執筆の妨げにならない。
- 取り込み（Extracted）は原本を変えず、原本側の作業を続けられる。原本の更新は、取り込み済みの資産の「変更あり」として後から示す。
- 診断は、執筆中の人には控えめに、レビュー・CI・AIには網羅的に示す。
- 指標は移行の割合より、人の手戻りと中断の少なさを先に見る。

### D14. 生成物は、CIで再現できるかで仕分ける

文書の生成をGitHub Actions等のCIでも動かすため、MMIが作る生成物（展開した表、取り込んだ画像、シートの画像化の結果、索引）を次の2つに仕分ける。

| 区分 | 条件 | 扱い |
| --- | --- | --- |
| 再生成できるキャッシュ | 原本とMMIの版だけから、CIの上で決定論的に作り直せる | ローカル・CIのキャッシュに置き、Gitで管理しない。原本のダイジェストとMMIの版で失効させる |
| 管理する中間生成物 | CIの上では作り直せない（ExcelのCOM操作による描画、人が選んで確定した結果など） | 資産としてGitで管理する。出典（原本のダイジェスト、範囲、生成方式と版）を添える。CIは作り直さず、原本のダイジェストと照合して古くなっていないかだけを検査する |

管理する中間生成物は、手元で作り直す手間と、Gitに置く量の両方を増やす。そこで描画の方式は、次の順で選ぶ。

1. **CIで動く方式:** xlsxの中身（セル値、罫線、結合、塗り、貼られた画像の位置）からMMI自身が描画する方式、またはLibreOffice等のヘッドレスの変換器。Linux上で再現でき、生成物をキャッシュに留められる。
2. **手元でだけ動く方式:** ExcelのCOM操作。描画の忠実度は最も高いが、CIでは動かない。1で再現できない図形などに限って使い、結果は管理する中間生成物として扱う。

どちらの方式で作ったかを生成物に記録し、同じ範囲を別の方式で作った結果を同一とみなさない。

### D15. MMIと生成AIの関係は「利用される・軽量認知する・提案する」の3つとする

MMIは生成AIサービスそのものを内包するのではなく、次の3つの関係に集中する。

1. **外部LLMから呼び出され利用される。** CLI、skill、将来のMCP等を通じ、外部AIがsourceを丸読みせずにinspect / check / render / extract / manifest等を利用できるようにする。外部AIの選択、契約、課金は利用者側の責務であり、MMIは特定サービスを必須にしない。
2. **軽量の認知基盤で解析を補助する。** Fly-inspiredな疎表現、Jev類似のbounded model、ローカルLLM等を、Excelの構造発見・候補抽出・類似検索・閉集合判断に使う。ローカルCPUでの実行を優先し、MMIからの追加API課金を前提にしない。
3. **外部LLMに作業提案と判断材料を渡す。** MMIが解けない、または人・LLMの判断が適する箇所について、source locator、Candidate、evidence、provenance、診断、限定した抜粋から作業依頼やprompt packageを生成する。MMI自身は送信せず、利用者または外部AIがそれを使う。戻された提案はAuthority Planeで再検証する。

この境界により、外部LLMが進化してもMMIの価値は失われない。MMIは「推論モデル」ではなく、文書資産と人・AIの間で、構造、根拠、検証可能な操作を提供する基盤であり続ける。

### D15. 配布は最小ランタイムを優先する

MMIのCore・CLI・IDE連携・WASM等の各経路では、**必要な機能、安全性、再現性、互換性を満たす候補のうち、実行時依存と配布バイナリが最小になる方式を優先する。**

この原則は特定コンパイラへの固定を意味しない。GoをCore実装の有力候補としつつ、同じ契約とconformance corpusを満たせる場合はTinyGo等のsmall-binary toolchainを優先してよい。将来、標準Goに近い言語互換性・標準ライブラリ互換性を保ちながら、より小さなnative/WASMを生成できるHike類似の実装が十分成熟した場合も、比較対象に加える。

ただし「小さいこと」を機能・安全性より上位に置かない。次の条件を満たさないtoolchainへ合わせてCore機能を削らない。

- Authority Planeの同一入力・同一結果
- Read-only / Containment / Stable diagnostics
- Candidate / provenance / manifest等の公開契約
- 必要なSource Adapterとファイル処理
- 対応OS・WASM hostでの安定動作
- ライセンスと保守性
- conformance corpusの一致

実装はportable coreとhost-specific adapterを分離し、標準Go、TinyGo、将来の代替toolchainを差し替えて比較できる構造を保つ。VS Code拡張はTypeScriptの薄いhost adapterとして残してよい。

## 製品の優先度

利用者向けの最優先は、既存Excel設計書を踏襲したMarkdownとの共存と、新しいExcel表も使えるVS Code上の執筆である。要求EW01〜EW07を一連の作業で確かめ、不足を直す。以下の番号は共通基盤と能力を整える順序として維持し、執筆の受入をCLIや新しい候補種別の実装完了まで待たせない。

- AI向け指示パックとmachine-readable output

## 評価指標

まず、既存設計書を使って書けた本文、新しいExcel表の参照、保存後の値確認、構造変更後の参照修正、迷いや中断と追加の手間を見る。コードの検査、実VS Code・Excelでの操作、書き手の価値確認を別々に記録する。

従来の「表が正本と一致するか」に加え、次を追う。

1. 既存文書から有用なCandidateを見つけられた割合
2. inferred candidateの採用・修正・却下率
3. 既に取り込んだ資産を再作業した件数
4. 人が原本を開いて目で確かめる回数の減少（原本を使わなくなることではなく、確かめるために開く手間）
5. Linked → Extracted → Detachedへ移せた情報単位の割合（人が移すと決めた範囲に対して）
6. detach check後に原本を外して発生した欠落件数
7. AIがmanifestとdiagnosticsだけで修正できた割合
8. 外部AIを使わずローカルで完結できた候補抽出の割合
9. 利用者が価値確認を済ませたモダナイズシナリオ数

人の作業を止めた回数（候補の採否・診断のために執筆を中断した回数）を、移行の割合より先に見る。速度だけをKPIにしない。人が選んだ併用・移行の形で書き続けられ、情報欠落と誤確定を増やさないことを主な成功条件とする。

## 受け入れるトレードオフ

- 対象形式と候補種別が増えるため、単純な表参照ツールより設計範囲は広がる。
- 全形式を一度に対応せず、Candidate contractとprovenanceを先に固定して縦に広げる。
- 軽量認知を中核に置くが、自動確定率を最大化しない。曖昧な場合に止まることを品質とみなす。
- 元文書とMarkdownの継続併用には、保存後の更新確認と参照修正の経路が必要になる。Linkedを正当な継続運用として支える。
- MMIから離脱可能にするため固有形式への囲い込みは避ける。これは継続利用率だけを見れば不利だが、企業文書の基盤としての信頼性を優先する。
