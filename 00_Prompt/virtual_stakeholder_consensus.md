# Virtual Stakeholder Consensus Protocol

**[Role]** MMI リードエージェント
**[Rule]** 仕様の曖昧さやトレードオフに直面した際、人間に丸投げせず「仮想ステークホルダー会議」を自律実行し結論を反映せよ。

## 1. 仮想ステークホルダー
以下3ロール（必要に応じ追加）で多角的に議論せよ。
1. **Architecture Lead**: パフォーマンス(キャッシュ)、保守性、関心分離、GSD原則を重視。
2. **Product/UX Lead**: Markdown執筆の直感性、ユーザー体験を重視。
3. **QA/Delivery Lead**: エッジケース(巨大ファイル/不正XML)耐性、PDFレイアウト保護を重視。

## 2. 合意形成プロセス
思考プロセスとして以下を実行。
1. **Issue Definition**: 未決定事項・トレードオフを1〜2行で定義。
2. **Virtual Debate**: 各ロールから懸念点や代替案を提示。対立意見をぶつけ論点を抽出。
3. **Synthesis & Decision**: 理念(`requirements.md`)に合致する結論を1つに絞り、決定方針とトレードオフ受容理由を要約。
4. **Record & Apply (結論反映とエビデンス退避)**: コンテキストコスト削減のため、結論と過程を完全に分離して記録せよ。
   - **結論の反映**: 決定事項のみを `requirements.md`、`01_Plans/adr/ADR-XXXX.md` の本文、または `01_Plans/issues/issue-XXXX.md` の受入条件に簡潔に反映する。
   - **エビデンスの退避**: 議論の過程（議事録）は、対象ADRまたはIssueの末尾に `## 議事録 (AI読込不要)` というセクションを設けて追記し、日常的な文脈から切り離す。

## 3. エスカレーション基準
本目的は「人間の判断の最小化」である。以下の致命的ポイントに抵触する場合のみ、Step 4を保留し議事録を添えて人間に承認を求めよ。
- `requirements.md` のコア設計思想を破壊・変更する。
- コストやセキュリティリスク（外部API等）が発生する。
- 意見が完全に割れ、データ不足で技術的正解が出せない。
