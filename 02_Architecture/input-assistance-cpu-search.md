# CPUでの範囲探索と自然言語入力

- 状態: Proposed（評価用の実装と実測あり、§7。製品UIは未実装）。FlyHashは条件付き採用（§7.5）。
- 対象: 構造索引、限定文法の解析器、候補検索の比較評価
- 関連: [ADR-0016](../01_Plans/adr/ADR-0016-notation-first-input-assistance.md)、[issue-0115](../01_Plans/issues/issue-0115-cpu-range-search.md)、[ソースモデル](input-assistance-source-model.md)、[クリップボード出所](input-assistance-paste-provenance.md)

自然言語または貼り付け断片から、Excelの表領域と既存MMI記法を探す。外部推論API・GPU・ニューラル埋め込み・ローカルLLMを必須にしない。§1〜§6は設計、§7は実測の記録である。

## 1. 責務の分離

```mermaid
flowchart LR
  E[原本を読み取り専用で解析] --> S[領域・見出し・型の索引]
  N[自然言語または貼り付け断片] --> L[字句解析・辞書]
  L --> A[限定文法の構文解析]
  A --> I[未解決の参照モデル]
  I --> R[完全一致索引 / 近似候補検索]
  S --> R
  R --> V[原本と厳密照合・意味検査]
  V --> C[既存MMI記法へ変換]
  C --> P[候補・根拠・プレビュー]
  P --> U[選択して挿入]
```

近似検索は**候補を速く絞る部品**にすぎない。意味の理解と範囲の確定を担わせない。最終判定は必ず原本との厳密照合で行う。

## 2. 索引

### 2.1 何を索引化するか

[ソースモデル](input-assistance-source-model.md)の`SheetSource`を入力とし、**領域単位**で索引化する。全矩形を列挙すると組合せが膨らむため、矩形の総当たり生成は行わない。

| 項目 | 内容 |
| --- | --- |
| 領域 | シート名、定義済みテーブル・名前付き範囲、使用範囲、推定した表領域。すべて原本のA1座標に結び付ける |
| 見出し | 見出し候補行・列、周辺の表題セル |
| 型 | 列ごとの型比率（`s`/`n`/`d`/`b`/`e`）、空欄率 |
| セル | 厳密照合用の表示文字列、型、生値、数式の有無、結合範囲 |
| 転置索引 | 表示文字列 → (領域, 原本座標)。貼り付け断片のアンカー検索に使う |

空行だけで表の境界を断定しない。複数表・階層見出し・結合セル・注記を考慮し、境界が不確かな候補にはその理由を付ける。結合範囲は`!merges`から取り、空白セルから推定しない。

索引にはセル内容に由来する情報が含まれる。ローカル保存・明示した対象のみ・削除可能とする。

### 2.2 更新とキャンセル

- ファイルのmtime・サイズをキーに差分更新する。1キー入力ごとに全ブックを再読込しない。
- Workerで初回解析と検索を実行し、キャンセルと更新競合を扱う。
- 候補確定時に原本を再確認する。索引はブック更新で失効させる。

### 2.3 切り出しの実測値

住所指定の切り出しは、200,000行×40列・実セル1,142,880個の疎シートに対して`C5:F12`で0.05〜0.20ms、`B100000:K100200`で0.19〜0.48msだった（3回の実行の幅。詳細は[ソースモデル](input-assistance-source-model.md)§2）。切出しだけの計測である。読込み・領域検出・索引構築・差分更新・検索・原本再照合は§7で別々に測った。

## 3. 自然言語の解析

### 3.1 入口の範囲

自由会話ではなく、ブック名・シート名・表名・列名・限定操作の組合せを受け付ける。最初の対象は明示的な依頼とする。

```text
入力 → 字句解析 → 構文解析 → 未解決の参照モデル
     → ブック/シート/列の名前解決 → 型・意味の検査
     → 候補プレビュー → 既存MMI記法への変換 → 既存パーサーで再検査
```

内部モデルの例。**新しい公開記法ではない。**

```json
{"sourceHint":"設計.xlsx","sheetHint":"状態遷移","range":"C5:F12","operations":[],"unresolved":[]}
```

検証後の出力は既存文法のみ。

```markdown
![[./data/設計.xlsx#状態遷移|C5:F12]]
```

### 3.2 特徴

日本語の文字n-gram、識別子、列見出し、業務用語辞書を基本特徴とする。必要なら軽量な形態素解析を比較する。表側と問い合わせ側を同じ特徴空間へ写像し、見出し・表題・値の役割は別の特徴として扱う。ニューラル埋め込みは初期要件にしない。

### 3.3 対応する例と対応しない例

| 入力 | 扱い |
| --- | --- |
| 「状態遷移表のIDと操作を見せて」 | 表題・見出しから領域を探し、`columns`で対応列を指定 |
| 「リリース判定の表から要確認を含む行を見せて」 | 対象を選び`grep=要確認`へ変換 |
| 「このコピー元の範囲を参照したい」 | クリップボードの出所・矩形照合の経路へ |
| 「担当者別に集計」 | 未対応。既存文法に集計は無い |
| 「判定列が完全に一致する行」 | 未対応。`grep`は行全体の部分一致であり意味が違う |
| 「最新のものだけ」 | 未対応。並べ替え・比較は既存文法に無い |

`grep`への安易な置換をしない。記法仕様§6の`grep`は「本体行のいずれかのセルに大文字小文字不問の部分一致」であり、列を指定した完全一致とは意味が異なる。否定・比較・並べ替え・同名列・未知語を黙って削除しない。意味検査で対応可否を判断し、未対応は理由を示す。

画面には文法が受け付ける入力の短い例を示す。自由な日本語をすべて理解すると約束しない。解釈結果は「対象: リリース判定 / 条件: 行のどこかに要確認を含む」のように説明してから候補を選ばせる。

### 3.4 解析器の実装方針

小さな限定文法なら手書きの解析器で足りる可能性がある。規則が増える場合は字句と構文を分離できる既存ライブラリ（Chevrotain等）を比較するが、**依存追加は未決定**。評価軸は、編集途中の入力、引用された日本語名、エスケープ、診断位置を扱えるか。生成時だけでなく既存参照の編集にも同じ検証を使う。

## 4. 候補検索方式の比較

### 4.1 比較対象

同じ特徴・同じデータ・同じ候補数で比較する。

| 方式 | 位置付け |
| --- | --- |
| 完全一致の転置索引 | 基準。貼り付け断片の厳密照合はこれに依存させる |
| 文字n-gram + TF-IDF / BM25 | 語彙検索の基準 |
| 単純な疎ベクトル類似度 | 素朴な基準 |
| FlyHash | 評価対象 |

### 4.2 FlyHashの位置付け

疎な特徴 → 固定seedの疎射影 → winner-take-allによる疎なタグ → 上位候補検索 → 厳密な再順位付け、という構成で評価する。原論文は画像・単語ベクトルの類似検索を対象としており、日本語からの特徴生成やExcel座標の解析を含まない。**論文の結果をMMIのCPU速度や精度の実測値として扱わない。**

- 射影出力数m、各出力の接続数s、活性数kは固定値を先に正解とせず、測定で選ぶ。
- 素朴な射影計算は概ねm×sの加算、上位選択は実装次第でm log k程度。N領域の活性ID保存はN×k程度だが、転置索引と原本モデルの容量は別に測る。
- 生物学上の次元数・活性率をそのまま最適値にしない。
- 特徴空間に存在しない同義語はハッシュだけでは扱えない。業務辞書と表題・列名の対応で補う。
- 固定seed、特徴辞書の版、射影設定を保存し再現できるようにする。活性ビット→領域IDの索引が必要で、全ハッシュの総当たりでは意味がない。

### 4.3 採用条件

固定した評価セットで、基準方式以上の候補再現率を保ちつつ、検索と照合を合わせた遅延またはメモリに実益があること。差が無ければ単純な方式を採用する。論文に合わせるために製品を複雑化しない。小規模では索引構築と再順位付けの負担が単純検索を上回り得る。

判断は採用・条件付き採用・見送りのいずれかを根拠付きで記録する。FlyHashの採否を待って、Excel範囲貼り付けと補完を止めない。

## 5. 測定の手順

### 5.1 記録する条件

CPU型番・コア数、RAM、SSD、OS、Node、ブック総容量、セル数、候補領域数、最大シート、索引設定、seed、反復数。

### 5.2 規模

10 / 100 / 1000ブック、1千 / 1万 / 10万の領域候補を段階的に用意する。**候補領域数とブック数は独立した規模指標として報告する。** 合成データと業務を模した架空データを区別する。

### 5.3 分けて測る項目

初回読込、索引構築、差分更新、warm検索、厳密照合。それぞれp50/p95とピークメモリ。索引メモリとcold/warmの時間を分ける。CPUのみで実行した証拠を残す。

### 5.4 評価データ

- 正解座標付きのコピー検証を30件以上。
- 自然言語の依頼を60件以上。完全名・略称・言い換え・誤字・同名・未対応条件・該当なしに分ける。
- 正解のブック・シート・範囲と許容する候補を人手で固定する。
- **辞書調整用と未見の評価用を分ける。** 評価データで辞書を合わせ込まない。

### 5.5 指標

Recall@5、最上位正解率、棄却率、誤った確定数、待ち時間。正解が存在する依頼のRecallと、該当なしを棄却する精度を分けて報告する。

### 5.6 目標と必須条件

| 区分 | 内容 |
| --- | --- |
| 採用目標（未測定・保証値ではない） | warm検索p95 100ms以内、厳密照合を含めてp95 300ms以内、自然言語のRecall@5 95%以上 |
| 必須条件 | 誤った範囲の自動確定0件、原本変更0件、クラウドAPI呼出し0件 |

目標に届かない場合は、候補数・対象規模・対応する言語表現の範囲を見直す。**LLMへ自動で切り替えない。**

## 6. 費用の前提

主経路はLLMを使わない。ただしCPU・メモリ・初期索引構築・更新のコストは残るため「費用も計算量もゼロ」とはしない。初回のExcel読込と索引構築は別に計測し、進行表示とキャンセルを必須にする。

非GPU環境のローカルLLMが本用途で必ず遅いと実証したわけではない。利用者の想定と優先順位に従い、必須構成から外している（[issue-0113](../01_Plans/issues/issue-0113-local-ai-feasibility.md)は保留）。

## 7. 実測結果（2026-09-24）

実装: `03_Implement/src/search/`（領域検出・カタログ・4方式の検索・限定文法コンパイラ・原本再照合）。評価: `03_Implement/scripts/cpu-search-eval/`（`npm run eval:cpu-search`、`npm run eval:cpu-search:scale`）。単体テスト: `test/cpuSearch.test.ts`。

### 7.1 環境

Intel Core i7-1365U（論理12コア）、RAM 7.6GiB（WSL2割当）、WSL2 Ubuntu（Linux 6.18 microsoft-standard）、Node v20.20.2。GPU・ネットワークは不使用（評価コードは外部通信するモジュールを読み込まない）。seed 20260924、架空業務データの時間は30反復。**Windowsネイティブではなく同一機のWSL2で測定した。** OSのページキャッシュは温まった状態（直前に書き出したファイル。キャッシュ破棄にはroot権限が要るため未実施）で、「初回読込」はプロセス内で初めて読む時間を指す。

### 7.2 架空業務データ（32ブック・49領域）

受注・会計の2システムと共通の工程文書を模した。同名シート（画面一覧・テーブル一覧）、1シート複数表、A1以外の起点、結合・分離・密着の表題、`Sheet1`、重複見出しを含む。生成器は`corpus.ts`（固定seed）。

**領域検出:** 49/49件の範囲と表題が正解と一致した（全矩形の列挙なし）。見出しの確度は48件が`likely`、1件が`uncertain`（全列が文字列で値の重複もある`ファイアウォールルール`）。

**時間（p50/p95、ブックあたり）:** 読込 0.69/1.82ms（合計33ms）、領域検出 0.05/0.12ms、索引の全構築 30ms、差分更新（1ブックのmtime変更→再読込・4領域の入替え）4.6ms。warm時の検索のみ・コンパイル全体・原本再照合込みは、どの方式もp95 0.5ms未満。採用目標（100ms／300ms）を大きく下回るが、**49領域という小規模での値**であり規模の評価は§7.3による。

**品質（Recall@5は正解のある依頼、棄却率は未対応・該当なしの依頼）:**

| 評価セット | 件数 | 完全一致 | BM25 | コサイン | FlyHash | 棄却率 |
| --- | --- | --- | --- | --- | --- | --- |
| 調整用（dev） | 36 | 0.852 | 0.963 | 0.963 | 0.963 | 1.0（全方式） |
| 未見v1（凍結して1回評価） | 40 | 0.600 | 0.667 | 0.667 | 0.667 | 1.0 / 0.9 / 0.9 / 0.9 |
| 未見v2（v1の分析後に凍結して1回評価） | 40 | 0.533 | 0.667 | 0.667 | 0.633 | 0.8（全方式） |
| 未見v3（v2の分析から一般規則を足し、凍結して1回評価。コミット`3e04d94`） | 40 | 0.667 | **0.800** | **0.800** | 0.767 | 1.0 / 0.9 / 0.9 / 0.9 |

未見v3の内訳（BM25のRecall@5）: 完全名0.875、略称0.833、言い換え0.500、誤字1.0、同名1.0（該当する全候補を提示）。未対応5件は全方式で棄却、該当なし5件のうち4件を棄却。辞書なしでは0.767（辞書の寄与+0.033）。

- 未見セットは、辞書・調整用セット・実装を見ない独立したエージェントが正解表から作成した。v1で得た失敗分析を反映したため、v1は以後「未見」ではない。v1の分析で直した後の値（v1 0.967、盲検ではない）は汎化の根拠にしない。**実際に汎化したかはv2で測り、0.667にとどまった。**
- 未見セットでの失敗は、**4方式ともほぼ同じ依頼で起きた**。原因は検索方式ではなく限定文法の網羅不足（活用した動詞、口語の言い回し、「〜が出てるもの」等の条件表現、略称）。検索方式を替えても改善しない。
- 業務辞書（調整用セットだけで作成）は調整用で+0.15、未見v1で+0.03〜0.07、未見v2で±0だった。**辞書は作成時に見た言い回しにしか効いていない。**
- v2の失敗から、個別の言い回しではなく**一般規則**を加えた: 2文目以降は補足（ただし未対応の目印は数える）、「Xに／へ＋動詞」は貼り付け先、口語・丁寧の動詞形と複合助詞、「Xが出てる」は行全体の部分一致、「XがVする…の表」は表の説明（動詞の無い「判定がNGの表」は列条件として棄却のまま）、構造名詞（一覧・表）は一致を求めない、括弧の限定語は必ず一致を求める、集計・並べ替え語は索引に同名の見出しがある場合だけ名前として扱う。**未見v3で0.667→0.800に上がった。**安全面の後退は無い（未対応の誤受理0件）。
- **近い候補（2026-09-24）:** 名前で一致する表が無いときだけ、名前の一部（被覆率0.25以上0.5未満）が一致する表を最大3件、「近いかもしれない表（名前は一致しません）」として別枠で示す。判定は「該当なし」のままなので、上表のRecallと棄却率は変わらない。未見v3で取りこぼした6件のうち2件は正解の表がこの別枠に入った。該当なしの依頼に別枠が出たのはv1〜v3で計3/15件。選べば通常どおり確認段で表示を確かめてから挿入する。
- 採用目標のRecall@5 95%には未見セットでまだ届かない。残る失敗の中心は言い換え（0.500）で、表題・見出しに無い語で表を説明する依頼である。§5.6に従い対応する言語表現の範囲を見直す（LLMへは切り替えない）。

**必須条件:**

- 誤った範囲の自動確定0件。コンパイラは常に最大5件の候補を返し（`requiresSelection: true`）、挿入する経路を持たない。
- 原本変更0件。読込みは読み取り専用。差分更新の測定で変えるのは、評価用に生成した一時ファイルのmtimeだけ。
- クラウド呼出し0件。
- **未対応条件の`grep`への置換:** 未見v2の1件（「性能測定結果の判定列がNGの行だけ見たい」）が`columns=E&grep=NG`へ変換されていた。v1分析後に追加した「〜の行」規則が、「X列が」を列条件として扱っていなかったことによる**安全上の不具合**で、修正した（`X列が／は…`を列条件として棄却し、未対応の目印を複合語へ結合しない）。修正後は全セットの未対応15件がすべて棄却される（v2のRecall@5は0.633、棄却率は0.9。盲検ではない）。該当なしの依頼のうち既存の表に近いもの（「総合テストケース」と結合テストケース、「給与テーブル」と受注テーブル定義）は候補として表示されるが、確定はしない。

### 7.3 規模（合成データ）

`scale.ts`で、業務名詞の組合せによる表題・4列の見出し・4行の本体を持つ表を生成した（1表21セル、1シート最大200表）。ブック数と領域数は独立に変え、組合せごとに別プロセスで測った（ピークRSSはその組合せだけの値）。問い合わせは一意な表題から200件（表題そのまま4割、表題＋列名3割、表題の1文字誤り3割）を作り、3反復した。**合成データであり、§7.2の業務データとは言い回しの難しさが違う。** 領域数の影響をみるための値で、品質の根拠にはしない。

**時間（ms）と記憶域。** 読込・検出はブックあたりのp50/p95、索引構築は4方式全部の同期（共有コーパスの構築を含む）:

| 10 | 1千 | 1.0MB | 13.7 / 25.2 | 142 | 37 | 278 | 31 | 147MB |
| 100 | 1千 | 2.4MB | 3.7 / 7.8 | 446 | 59 | 520 | 13 | 151MB |
| 1000 | 1千 | 16.6MB | 1.2 / 2.8 | 1,489 | 89 | 520 | 12 | 160MB |

### 7.4 FlyHashのパラメータ

10万領域（100ブック）の合成データで、m∈{1024, 4096, 16384}、s∈{4, 8, 16}、k∈{16, 32, 64}と再順位付けの有無の54通りを測った（`flyhashSweep.ts`、200問）。指標は網羅的なコサイン検索の上位5件との一致率。同じ特徴の上でコサインを近似する部品として、FlyHash自体の性能をみるためである。コサインのp95は151ms。

| 設定 | 一致率@5 | p95（ms） | 構築（秒） |
| --- | --- | --- | --- |
| m=4096, s=16, k=64 | 0.946 | 66 | 24 |
| m=1024, s=8, k=32 | 0.930 | 77 | 12 |
| m=4096, s=8, k=32（§7.3で使った既定値） | 0.916 | 30 | 13 |
| m=4096, s=4, k=16 | 0.906 | 11 | 8 |
| m=16384, s=4, k=16 | 0.899 | 2.6 | 8 |
| 再順位付けなし（54通りの最良） | 0.72 | — | — |

- **厳密な再順位付けは必須。** 無しでは一致率が0.72を超えない。
- どの設定でもコサインの結果を完全には再現しない（最良0.946）。速度と一致率は交換関係にあり、sとkの組合せで単調に変わらない。m・s・kは用途の規模ごとに測って選ぶ必要がある。
- 構築は他方式の約10倍遅い（射影の配線を特徴ごとに求めるため）。

### 7.5 FlyHashの判定: 条件付き採用

**根拠:**

1. **1万領域以下では採用しない。** 業務データ（49領域）と合成1千〜1万領域では、全方式が採用目標の時間を大きく下回る。FlyHashのRecall@5はBM25と同等かそれ以下で、構築は約10倍遅い。§4.3の「差が無ければ単純な方式」に従い、既定はBM25とする。
2. **10万領域ではFlyHashだけが時間の目標を満たした。** BM25はp95 157〜238msで100msを超え、FlyHashは33〜60msだった。代わりにRecall@5は4〜7ポイント下がる（0.90〜0.93 対 0.96〜0.97）。索引のヒープはBM25より約4割小さい（78MB 対 133MB）。
3. **採用する条件:** 索引済み領域がおよそ5万を超えてBM25のp95が目標を超える場合に限り、候補の絞り込みにだけ使う。常に厳密な再順位付け（コサイン）と原本との照合を通し、m・s・kは対象規模で測って固定する（seed・特徴辞書の版と一緒に保存する）。**意味の判断と範囲の確定には使わない。** 貼り付け断片の厳密照合（内容照合）にも使わない。
4. **品質の上限は検索方式ではない。** 未見の自然言語でのRecall@5は、方式によらず0.63〜0.67にとどまった（§7.2）。FlyHashの採否はこの課題を解決しない。次に効くのは限定文法の網羅（活用・口語の条件表現・略称）と、候補の提示・選択のUIである。

**未実施・限界:** Windowsネイティブ環境での測定、OSのページキャッシュを破棄した初回読込、コピー検証30件（内容照合側の正解付き評価。issue-0114の範囲）、VS Code上のUI（issue-0110/0111で扱う）、Workerスレッドでの実行（現状は協調的な中断のみ）、10万領域を超える規模（本環境の記憶域ではほぼ上限）。
