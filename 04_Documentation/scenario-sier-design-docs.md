## Target reader
- SIer の設計書・納品文書を作成する担当者
- Word / Excel 中心の設計書から Markdown ベースへ移行したいチーム

## Prerequisites
- 設計項目の正本として Excel / CSV / XML を維持していること
- Markdown をレビューや差分管理に使いたいという合意があること
- 「巨大表をすべて本文に展開しない」運用を受け入れられること

## Expected result
この文書を読むと、Markdown Matrix Injector を SIer 文書運用にどう当てはめるか、どの機能がどの課題に効くかを具体的にイメージできます。

## 適用条件 / 非推奨条件（適用しない条件）
### 適用条件
- 設計書本文は差分レビュー可能なテキスト（Markdown）に移し、一覧データは正本（Excel/CSV/XML）で管理したい。
- 監査・レビュー時に「必要断面のみ」を抽出し、証跡として残したい。
- 納品PDFで改ページ・向き・別紙参照を再現可能にしたい。

### 非推奨条件（適用しない条件）
- 外部正本を持たず、本文内の手入力テーブルだけで全情報を管理したい。
- Smart Fallback（カード化 / 別紙参照）を許容できず、全表を常時本文へ完全展開する方針である。
- レンダラ差異（CSSやPDFエンジン差）を吸収する調整工数を確保できない。

- 要件4: 本文の判断性を維持するため、比較証拠は本ファイル内に完結させる（samples 側への依存前提を置かない）。

## issue-0017 比較観点の固定（Scenario本文の受入条準拠）
- 本Scenario本文では、比較観点を **時間短縮（工数） / 品質（整合性） / 監査容易性（証跡性）** の3軸に固定する。
- 追加観点（レビュー再現性）は補助軸として扱い、必須判定は上記3軸で行う。
- 各観点は必ず「操作手順・期待結果・制約」を1セットで記述し、導入可否を本文単体で判断できる状態を維持する。

## ROI比較表（利用前 / 利用後）
| 比較観点 | 利用前（従来: Word/Excel中心） | 利用後（MMI活用） | 評価指標（例） |
|---|---|---|---|
| 時間短縮（工数） | レビュー対象行を都度Excelで探索し、Wordへ転記。差分確認も手作業。 | `grep`/`columns`/`header` で必要断面を本文へ直挿入し、レビュー準備を定型化。 | 1レビューあたり準備時間（分）、差分確認ステップ数 |
| 品質（整合性） | 本文と正本の二重更新が発生し、転記漏れ・転記ミスが混入しやすい。 | 正本はExcel等に一本化し、本文は参照表示に徹するため整合性を保ちやすい。 | 指摘件数（整合性起因）、再提出回数 |
| 監査容易性（証跡性） | 監査時に根拠行を再探索し、どの条件で抽出したかを説明しづらい。 | 抽出条件をクエリとして記述し、同一条件で再現可能なレビュー証跡を残せる。 | 監査質問への回答時間、再現手順の有無 |
| レビュー再現性（属人化抑制） | 担当者ごとに抽出観点や整形手順が異なり、レビュー品質がぶれやすい。 | 観点別に手順・クエリ・期待結果をテンプレート化し、担当者が変わっても同じ手順で再現しやすい。 | 手順逸脱件数、引き継ぎ時の立ち上がり時間 |

## 観点別: 操作手順・期待結果・制約（本文単体での導入判断用）
### 観点1: 時間短縮（工数）
- 操作手順:
  1. 設計書本文に `![[...]]` で対象シート範囲を挿入する。
  2. `?header=first&columns=A,C,F&grep=AUTH` のようにレビュー断面を指定する。
  3. 章ごとに必要断面だけを残してレビュー依頼する。
- 期待結果:
  - レビュー準備での「抽出・転記・整形」の繰り返しを削減し、準備工数を短縮できる。
  - レビュアーが本文から直接対象断面を確認できる。
- 制約:
  - 抽出条件（grep語彙や列定義）の運用ルールをチーム内で先に決める必要がある。
  - 正本側の列名/構造変更時は、参照クエリの追従更新が必要。

### 観点2: 品質（整合性）
- 操作手順:
  1. 正本を Excel/CSV/XML として維持し、本文は参照専用にする。
  2. 大規模表は `mode=card` または Smart Fallback で別紙参照化する。
  3. `caption`/`id` を付け、本文中の説明と参照位置を固定する。
- 期待結果:
  - 本文と正本の二重編集を避け、転記ミスや古い表の残存を抑制できる。
  - 本文は説明責務、正本はデータ責務と役割分離できる。
- 制約:
  - すべての情報を本文展開したい読者には、カード表示が情報不足に見える場合がある。
  - PDF出力品質はレンダラ/CSS設定に依存するため、初期調整が必要。

### 観点3: 監査容易性（証跡性）
- 操作手順:
  1. 監査観点に応じて `grep`/`highlightColumn`/`highlightValue` を設定する。
  2. 監査対象セクションに抽出条件を明記し、同一リンクを保持する。
  3. 必要に応じて `formatColumn=E:json` で設定値列を可読化する。
- 期待結果:
  - 「どの条件で、どの行を確認したか」を再現可能な形で残せる。
  - 指摘時の再確認が高速化し、監査説明の一貫性が高まる。
- 制約:
  - 監査要件が非定型（都度異なる抽出規則）の場合、テンプレート化に限界がある。
  - 機密情報列を扱う場合、表示範囲やマスキング方針を別途定義する必要がある。

### 観点4: レビュー再現性（属人化抑制）
- 操作手順:
  1. レビュー論点ごとに「抽出クエリ」「見るべき列」「期待結果」を文書テンプレートとして固定する。
  2. 各章の冒頭にテンプレートへの参照（例: 監査観点A/B/C）を記載する。
  3. レビュー実施後は、テンプレートとの差分（追加クエリ・例外条件）を追記する。
- 期待結果:
  - 担当者交代時も同じ観点でレビューを再実行でき、引き継ぎ負荷を下げられる。
  - レビュー品質が個人スキル依存になりにくく、運用の安定性が上がる。
- 制約:
  - テンプレートの維持管理責任（更新タイミング・承認者）を決めないと形骸化しやすい。
  - 案件固有の例外が多い場合、共通テンプレートだけではカバーしきれない。

## Scenario 1: 設計書本文は Markdown、一覧正本は Excel
課題:
- 設計書本文は Markdown で差分管理したい。
- ただし、権限定義表や状態遷移表の正本は Excel のまま維持したい。

使い方:
- 設計書本文に必要な範囲だけ `![[...]]` で差し込む。
- レビュー対象の章では `grep`, `columns`, `header` を使って必要な断面だけを見せる。

価値:
- 本文は軽量なまま保てる。
- Excel 正本と本文の二重更新を減らせる。

## Scenario 2: 巨大表は別紙参照として扱う
課題:
- 数十列・数百セルの一覧は本文に展開すると読みにくく、印刷でも崩れやすい。

使い方:
- `mode=card` を明示する、または Smart Fallback に任せてカード表示へ縮退する。
- 印刷時は別紙参照ブロックとして扱い、本文側では要点だけを説明する。

価値:
- 本文の可読性を保ちながら、正本ファイルへの導線を残せる。
- 納品時の PDF 崩れやレビュー時の視線負荷を減らせる。

## Scenario 3: 監査・レビュー向けに必要箇所だけ抜き出す
課題:
- 監査やレビューでは、巨大な一覧の全件より「特定条件に一致する断面」だけを見たいことが多い。

使い方:
- `grep`, `columns`, `highlightColumn`, `highlightValue`, `formatColumn` を組み合わせる。
- JSON や設定値が入った列はコードブロック風に描画し、対象行だけをハイライトする。

価値:
- レビュー観点に合わせた断面を、そのまま Markdown 文脈内へ差し込める。
- レビュアーが元 Excel の全体を毎回開かなくてもよくなる。

## 導入可否の判定手順（Scenario本文のみで実施）
1. **適用条件** を確認し、自組織が「正本分離」「断面レビュー」「印刷制御再現」の3点を受け入れ可能か判定する。
2. **非推奨条件** に該当しないことを確認する（該当する場合は導入見送りを第一候補とする）。
3. **ROI比較表（利用前/利用後）** と観点別の「操作手順・期待結果・制約」を照合し、最低3観点で期待効果と運用負荷の釣り合いを判定する。
4. 3観点すべてで「期待結果を受容でき、制約に対する運用策を持てる」場合のみ、段階導入（章単位）を開始する。

## Decision Readiness Checklist
- 比較観点（利用前/利用後）を3項目以上（時間短縮・品質・監査容易性）で明示した。
- 各観点に、操作手順・期待結果・制約をセットで紐付けた。
- 適用条件 / 適用しない条件を明示し、導入可否を本文単体で判断できる構成にした。

## Known limitations
- Smart Fallback の最終見え方や印刷時レイアウトは、利用するレンダラや CSS と組み合わせて調整が必要です。
- 公開文書では一般的なシナリオに絞っており、組織固有テンプレートや社内ルールへの適用は別途設計が必要です。

## FAQ（Scenario）
### Q1. どのシナリオから試すべきですか？
A1. まず Scenario 1（Markdown 本文 + Excel 正本分離）から開始し、次に Scenario 2（巨大表カード化）へ進むと移行コストを評価しやすくなります。

### Q2. ROI 比較表の数値が小さい場合でも導入価値はありますか？
A2. あります。時間短縮だけでなく、監査容易性・再現性の改善も判断軸に含め、3 観点合算で評価してください。

### Q3. 組織固有ルールが多い場合は適用不可ですか？
A3. 不可ではありません。共通テンプレートを基準にしつつ、例外条件を章ごとに明記する運用設計が前提になります。
